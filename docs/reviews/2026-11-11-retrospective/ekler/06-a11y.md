# 06 — Runtime Accessibility (A11Y)

## Area summary

I tested every shipped component in a real browser (Storybook 8.6.18, Chromium through playwright-cli session `a11y`). I ran **axe-core 4.10.2** on **all 257 stories**. The tag set was wcag2a/aa, wcag21a/aa, wcag22aa and best-practice; page-level rules region, landmark-one-main and page-has-heading-one were off. axe returned 0 run errors and 12 rule types with violations.
I also checked the **Chromium accessibility tree** through CDP `Accessibility.getFullAXTree`, which is the ground truth for names, roles and states. I ran keyboard scripts (Tab, arrow keys, Space/Enter, Escape, F6), forced-colors and reduced-motion emulation, a target-size sweep, 320 px reflow and a text-only-resize simulation.

**Verdict: Weak.** The behaviour layer is strong: roving focus, Escape, focus return, reduced motion and live-region design are good. But one root cause breaks the most-used controls: **ARIA and `<label>` wiring that crosses the shadow boundary**. As a result, **Checkbox, Radio, Select (all modes), icon-only Button and Progress have NO accessible name** in Chromium's accessibility tree. Unit tests do not catch this because they check attributes, not the computed accessibility tree.
Other blockers:
- Toast and Message action/dismiss buttons cannot be reached with the keyboard.
- The light-mode focus ring is 1.89:1.
- Switch, radio and indeterminate checkbox states disappear in Windows forced colors.

Raw evidence: `review\a11y-work\axe-all.json` (257 stories) and the scripts next to it. Screenshots are in `review\shots\a11y\`.

### AX-1: Checkbox and Radio have no accessible name
- Severity: Blocker
- Merge-blocking for current branches: No (on main since v0.7/v0.8; must be fixed before any release)
- Confidence: Verified
- Where: `packages/core/src/_internal/selection-control-base.ts:235-247` (`<label class="root">` wraps `<span role=checkbox|radio>`), `checkbox/tulpar-checkbox.ts:101-109`, `radio/tulpar-radio.ts:88`, `_ariaLabel()` at `selection-control-base.ts:196-198` (it returns `undefined` when a visible label exists).
- Problem: A `<label>` only labels *labelable* elements (button, input, meter, output, progress, select, textarea, form-associated custom elements). A `<span role="checkbox">` is not labelable. So the visible label text never becomes the name. When a visible label exists, `aria-label` is also removed. The result is that every labelled checkbox and radio is announced as "checkbox, not checked" with no name.
- Evidence: Chromium AX tree, story `components-checkbox--states`: `checkbox "" checked="false"` ×12 (the label "Checked", "Indeterminate" and so on is visible on screen). `components-radiogroup--states`: `radio "" checked="true"` ×16. `components-checkbox--required-with-message`: the host has `label="Accept terms of service"`, the AX name is `""`. axe `aria-toggle-field-name` (serious) fails on 35 stories (all checkbox, checkbox-group and radio-group stories). Switch is correct (`switch "Enable notifications"`) because its control is a native `<button>`.
- Why it matters: Screen-reader users cannot tell what they are agreeing to or choosing. This fails WCAG 4.1.2 Name, Role, Value and 1.3.1. It affects every form in every consumer app.
- Correct solution: Give the control an IDREF name *inside the same shadow root*. Render `<span id="label">…<slot name="label">` and put `aria-labelledby="label"` (plus `aria-describedby` for the description) on the `role=checkbox|radio` span. Both IDs live in the same tree scope, so they resolve. Slotted label content is included through the flat tree. This is what Shoelace/Web Awesome, Lion and Spectrum Web Components do for custom-role controls. Material Web and Fluent UI WC instead use a native `<input type=checkbox>` in the shadow root plus a native `<label for>` in the same root, which is even more robust. Industry direction: use a native input in the shadow root (Material Web `md-checkbox`, Web Awesome 3 `wa-checkbox`). Also add one regression test per control that reads the computed name (`page.accessibility` / `getComputedAccessibleNode` in WTR via Playwright launcher), not the attribute.
- Effort: M

### AX-2: Select trigger has no accessible name; searchable trigger is named by its value
- Severity: Blocker
- Merge-blocking for current branches: Yes for v0.15 (it extends the broken path to searchable), and pre-existing for v0.14.
- Confidence: Verified
- Where: `_internal/form-field-base.ts:268,275` (`<label for="control">`), `select/tulpar-select.ts:880-893` (`<div id="control" role=combobox|button>`), `aria-label=${ariaLabel ?? nothing}`.
- Problem: `<label for="control">` points at a `<div>`, which is not labelable, so the label does not give the name. A `combobox` also does not take its name from content. Result: `combobox ""`. In searchable mode the trigger is `role=button`, so its name comes from its *content* (placeholder or selected value). The field label is lost, and the name changes with the value.
- Evidence: AX tree, `components-select--validation`: `combobox "" desc="Please select a country to continue." invalid=true` (×3). `components-select--playground` (open): `combobox "" expanded=true focused=true`. `components-select--searchable`: `button "Select a city…" expanded=true`. axe `aria-input-field-name` (serious) fails on 13 Select stories. TextInput, NumberInput and Textarea are correct (native `<input>`/`<textarea>` + `<label for>`): `textbox "Invalid" desc="This field is required"`.
- Why it matters: The user hears "combobox, collapsed" with no field name. This fails WCAG 4.1.2 / 1.3.1 / 2.5.3 Label in Name (searchable). Select is the first Wave-2 brick toward the grid.
- Correct solution: In `FormFieldBase`, render the label with an `id` (`id="label"`) and set `aria-labelledby="label"` on the trigger (same shadow root). For the APG "Select-Only Combobox" pattern (https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-select-only/), the trigger keeps `role=combobox` in *both* modes. The current value is exposed as its text content, and the name comes from `aria-labelledby`. Do not switch the trigger to `role=button` in searchable mode. Also give the listbox `aria-labelledby="label"` (AX-22). Reference: React Aria `Select` and Spectrum WC `sp-picker` both name the trigger by labelledby to the field label.
- Effort: S

### AX-3: Icon-only / circle Button: host `aria-label` is never forwarded
- Severity: Blocker
- Merge-blocking for current branches: No (on main since v0.4)
- Confidence: Verified
- Where: `button/tulpar-button.ts:301-311` (`<button class="btn">` has no aria-label binding), `:213-214` (dev warning *tells* authors to put `aria-label` on the host). The tests in `tulpar-button.test.ts:265-304` only check that the warning is silent.
- Problem: The documented API is `<tulpar-button icon-only aria-label="Save">`. The attribute stays on the host, which has no role. The focusable inner `<button>` gets no name.
- Evidence: AX tree, `components-button--icon-only-variants`: `button ""` ×4. `components-buttongroup--editor-toolbar`: `button ""` ×6. axe `button-name` (critical) fails on 10 stories, and `aria-prohibited-attr` (serious) fails on 6 stories ("aria-label attribute cannot be used on a tulpar-button with no valid role").
- Why it matters: Every icon-only action (toolbar, card actions, close) is announced as "button". This fails WCAG 4.1.2. It also hits the future grid toolbars.
- Correct solution: Add an explicit `label` / `accessible-label` property that renders onto the inner `<button aria-label>`. This is the pattern in Shoelace/Web Awesome `label` on `wa-icon-button` and Spectrum `sp-action-button label`. Alternatively, use ElementInternals ARIA reflection by making the *host* the button (`internals.role="button"`, host `tabindex`), so host `aria-label` works natively. That is the Material Web 2 direction for some controls. Keep `aria-label`-on-host working by observing it and mirroring it to the inner control, then removing it from the host (the Lion `delegatesAria` pattern). That is valid as a *compat path* only. The long-term standard is the Reference Target proposal (`shadowrootreferencetarget`, in Chromium origin trial); until it ships, use explicit forwarding.
- Effort: S

### AX-4: Slotted-option Select: `aria-activedescendant` crosses the shadow root and never resolves
- Severity: Blocker
- Merge-blocking for current branches: Yes (v0.15 adds `searchable-slotted`, and slotted is the default authoring mode)
- Confidence: Verified
- Where: `select/tulpar-select.ts` virtual-focus reflection (~l.151-163, 227-232, 281). The active option id belongs to a light-DOM `<tulpar-option>`, but the attribute sits on the shadow trigger or search input.
- Problem: IDREF attributes resolve only inside the element's own tree scope. Light-DOM option ids cannot be referenced from inside the shadow root. Arrow keys move the visual highlight, but assistive technology gets no active option.
- Evidence: `components-select--playground` (slotted) after ArrowDown ×2: the AX combobox has **no** `activedescendant`, and all options report `selected=false`. axe on the open state: `aria-valid-attr-value` (critical) on `#control`. `components-select--searchable-slotted`: `aria-valid-attr-value` (critical) on `input[aria-label="Search Country"]`. Control check: data-mode (`components-select--data-prop-flat`, options rendered in the shadow root) **does** resolve (`activedescendant=…`, and the active option moves).
- Why it matters: In the default slotted mode, a screen reader user arrowing through the list hears nothing. This fails WCAG 4.1.2 / 2.1.1 in practice.
- Correct solution: Industry choice for WC selects with light-DOM options:
  (a) Move real focus to the options (roving `tabindex` on `tulpar-option`, listbox owns focus). Shoelace/Web Awesome `wa-select` and Spectrum `sp-picker` with `sp-menu` do this.
  (b) Put the combobox and the options in the same scope, by rendering mirrored option proxies in the shadow root (as data-mode already does), or by keeping the focus element in light DOM.
  (c) Use `ariaActiveDescendantElement` (ARIA element reflection), which *can* reference an element in a shadow-including ancestor scope. A light-DOM option is in the host's scope, which is *outside* the shadow root, so reflection works in Chromium/WebKit, with a Firefox gap until FF 136+. Verify per engine.
  Recommended: (c) with (a) as fallback, and a WTR test that reads the computed AX tree. Reference: https://w3c.github.io/aria/#ARIAMixin, WICG Reference Target explainer.
- Effort: M

### AX-5: K1 confirmed + searchable listbox / search-input structure
- Severity: Blocker
- Merge-blocking for current branches: Yes (v0.15)
- Confidence: Verified
- Where: `select/tulpar-select.ts:853-863` (`_renderSearch()` inside `role=listbox`), `:765-776`.
- Problem: K1 is reproduced in the browser. axe on the open searchable select reports `aria-required-children` (critical) on `#tulpar-select-listbox-2` (data mode) and `#tulpar-select-listbox-3` (slotted). The listbox contains a `combobox` input and `status` rows, which are not allowed children. In addition, the listbox has no name, and the trigger becomes `role=button` (AX-2). The resulting structure "button → listbox{combobox, options}" matches no APG pattern.
- Evidence: axe output in `sel.js` run: `aria-required-children:critical:1 [["tulpar-select","#tulpar-select-listbox-2"]]`.
- Why it matters: Screen readers may not expose the options or the search field correctly. NVDA and JAWS virtualize listbox children.
- Correct solution: Follow the APG "Editable Combobox with List Autocomplete" pattern in a popup. Structure: the popup is a generic container (or `role=dialog` with a label when it holds more than a list). It contains the search `<input role=combobox aria-controls=listbox aria-activedescendant>` as a *sibling* of `<div role=listbox aria-labelledby=label>`, and status rows outside the listbox (or `role=option aria-disabled` for "no match"). The trigger stays `combobox` (select-only) or becomes a plain button labelled "Country: İstanbul". Reference: React Aria `ComboBox` inside `Popover`, Atlassian Select, Ariakit `Select` with `Combobox` (https://ariakit.org/examples/select-combobox).
- Effort: M

### AX-6: Toast and Message buttons are unreachable by keyboard; F6 dead-ends
- Severity: Blocker
- Merge-blocking for current branches: No (v0.12 on main)
- Confidence: Verified
- Where: `toast/tulpar-toast.ts:270-276` (host `tabindex="-1"`), `_internal/toaster/toaster-root.ts:164-200` (F6 handler).
- Problem: A shadow host with a negative tabindex removes its whole shadow and slot scope from sequential navigation. So the dismiss `×` and the action buttons ("Discard", "Save now") are never reached by Tab. F6 focuses the region fallback (`firstFocusable` finds nothing across the shadow root), and the next Tab leaves to `body`.
- Evidence:
  - `feedback-toast--content-forms` → click "Two actions" → the shadow contains `Discard/Save now/×`. Then 9× Tab cycles only the story's trigger buttons and `body`.
  - `feedback-toast--stacking`: `F6 -> div[role=region][Notifications]`, then `Tab -> body`.
  - `feedback-toast--default` and `feedback-message--a-11-y`: F6 → body, Tab → body.
- Why it matters: Toast actions (Undo, Retry) are operable only by mouse. This fails WCAG 2.1.1 Keyboard (A). Also, 2.2.1 Timing Adjustable depends on pause-on-focus, which keyboard users can never trigger.
- Correct solution: Do not put `tabindex=-1` on the host. Make the toast card itself non-focusable and let its inner buttons stay in natural order inside the region. Give the region `role=region aria-label="Notifications (F6)"` and make it a focusable landmark with `tabindex=-1` on the *region*, not on each toast. On F6, focus the first toast's first focusable element, using a shadow-aware walker (`el.shadowRoot` recursion or `:focus-visible`-capable `focus({focusVisible:true})` on a known part). This is the Sonner/Radix Toast model ("Viewport" with a hotkey; toasts are list items with buttons in normal tab order). See https://www.radix-ui.com/primitives/docs/components/toast#keyboard-interactions. Add a WTR keyboard test: fire a toast with an action, press F6, then Tab → the action button is focused.
- Effort: S/M

### AX-7: Light-mode focus ring is 1.89:1 (fails 1.4.11); the token contrast test ignores alpha
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `packages/tokens/src/brand/tulpar/light.ts:119,325,354` (`rgba(81, 78, 207, 0.40)`), used by `button.styles.ts:458-461`, `selection-control-base.styles.ts:168-172,234-237`, `form-field-base.styles.ts:182-184`. Test bug: `packages/tokens/src/semantic/overlay.contrast.test.ts:7-10` ("alpha is ignored") and `:69-70`.
- Problem: The browser computed `outline: 2px solid rgba(81, 78, 207, 0.4)` on every focused button, checkbox, switch and chip. Composited on white it gives `#b9b8ec`, which is **1.89:1** against the white background (1.86:1 on `#f8fafc`). The minimum is 3:1 (WCAG 1.4.11 Non-text Contrast, which applies to focus indicators. 2.4.13 Focus Appearance (AAA) also needs ≥3:1 change). Dark mode (`rgba(132,151,255,.6)`) composites to about 3.2:1 on the dark surfaces, which passes narrowly. The unit test that should guard this compares the *opaque* colour, so it passes while the rendered ring fails.
- Evidence: Tab sequence output (`tab.js`): `tulpar-button>button.btn | outline:solid 2px rgba(81, 78, 207, 0.4)`. Screenshot `shots\a11y\light--button--all-variants.png` (the ring is barely visible). Contrast calculation in this report session.
- Why it matters: Keyboard users with low vision cannot find focus. This is a WCAG AA failure on every interactive control.
- Correct solution: Use an opaque focus colour with ≥3:1 against all surfaces it can sit on (kam-500 `#514ecf` on white is about 6.5:1), and use a 2 px outline with 2 px offset. Optionally use the "double ring" (inner surface-colour ring + outer brand ring) so it works on any background. GitHub Primer, Atlassian and Carbon use opaque focus tokens (`$focus` in Carbon = `#0f62fe`). Fix the test to alpha-composite the colour over the surface before computing contrast, and add a `color.focusRing` vs `color.bg.*` matrix test.
- Effort: S

### AX-8: Forced colors: switch invisible; checked radio and indeterminate checkbox lost
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: switch / radio / checkbox styles (`switch/*.styles.ts`, `radio/*.styles.ts`, `checkbox/*.styles.ts`). The base only handles the focus outline (`selection-control-base.styles.ts:173-178`).
- Problem: Under `forced-colors: active`, backgrounds are dropped. The switch track and thumb draw nothing, so only the label text remains. A checked radio's dot is gone, so all radios look unchecked. The indeterminate dash disappears, so it looks unchecked.
- Evidence: `shots\a11y\forced--switch--states.png` (no switches visible at all), `forced--radiogroup--states.png` (no checked radio; compare `light--radiogroup--states.png` where 4 are checked), `forced--checkbox--states.png` ("Indeterminate" looks identical to unchecked). Buttons, chips and select borders survive (`forced--button--all-variants.png`, `forced--chip--clickable-removable.png`). Minor issues in the same run: progress track is rendered dark red (`forced--progress--linear-determinate.png`), and disabled chips are not shown in `GrayText`.
- Why it matters: Windows High Contrast users (a large share of low-vision Windows users) cannot read the control state. This is a de-facto requirement for enterprise products (Section 508 buyers test it).
- Correct solution: Add `@media (forced-colors: active)` blocks:
  - Track and box: `border: 1px solid CanvasText`.
  - Checked fill: `background: Highlight` with `forced-color-adjust: none` only on the indicator.
  - Thumb, dot and dash: `background: HighlightText` / `CanvasText`.
  - Disabled: `GrayText`.
  Reference: Fluent UI WC switch/radio forced-colors styles, and Microsoft's guide https://learn.microsoft.com/fluent-ui/web-components/design-system/high-contrast. Add a Playwright screenshot test with `forcedColors: 'active'`.
- Effort: S

### AX-9: Progress `aria-labelledby` points into the shadow root; the progressbar is unnamed
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `progress/tulpar-progress.ts:218-222` (host `aria-labelledby=_labelId`), `:366` (`<span id=_labelId>` lives in the shadow root).
- Problem: The host is in the light tree, and the id is in its shadow root. The IDREF does not cross scopes, so the progressbar has no name even when `slot="label"` is used.
- Evidence: AX `display-status-progress--labels`: `progressbar ""` ×4 (story uses `<span slot="label">Uploading project assets…</span>`). axe `aria-progressbar-name` (serious) fails on all 8 progress stories.
- Why it matters: "progress bar, 58%" with no subject. This fails WCAG 1.1.1 / 4.1.2 for the labelled case.
- Correct solution: ARIA element reflection (`ariaLabelledByElements`) cannot fix this, because the spec allows references *out of* a shadow root, not *into* one. So move the role into the shadow root: render `<div role=progressbar aria-labelledby="label" aria-valuenow…>` next to `<span id="label">`. Both are in one scope. Native `<progress>` labelled by an in-shadow `<label for>` is the alternative (Material Web `md-linear-progress` puts the role on an inner div). Remove host `role`.
- Effort: S

### AX-10: Radio group: extra Tab stop on a role-less host before the radio
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `radio-group/tulpar-radio-group.ts:150-165` (sets `radio.tabIndex = 0/-1` on the **host**), `radio/tulpar-radio.ts:88` (inner `span[role=radio] tabindex=0`).
- Problem: The reachable radio has two tab stops. First the host (no role, browser default outline around a 1248×42 row), then the inner `role=radio` span. APG expects the group to be one tab stop that lands directly on the checked radio.
- Evidence: `components-radiogroup--default`: `Tab -> tulpar-radio[v=email]` (host, `outline:auto`, 1248×42), `Tab -> tulpar-radio>span[role=radio]`, `Tab -> body`. In the keyboard run, the first Tab lands on the host, and ArrowDown then moves into the inner span. Arrow navigation itself is correct.
- Why it matters: The first stop has no role or name, so screen readers announce nothing or "group". There is a redundant stop and a wrong focus visual. This goes against APG Radio Group (https://www.w3.org/WAI/ARIA/apg/patterns/radio/).
- Correct solution: Put roving tabindex on the *focusable control*, not the host. Use `delegatesFocus: true` on the radio's shadow root with the inner span as the only focusable element, and set the host `tabindex` only as the delegate. Better: make the host itself the radio (`internals.role="radio"`, `internals.ariaChecked`), as Material Web `md-radio` and Web Awesome `wa-radio` do. Then no inner focusable element and no double stop.
- Effort: S

### AX-11: Chip: host `role=button` contains a remove `<button>` (nested-interactive)
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `chip/tulpar-chip.ts:123` (host `role=button`), `:412` (inner `button.x`).
- Problem: A button inside a button is not allowed (button children are presentational). Assistive technology flattens it: the chip's name becomes "kaan@example.com Remove kaan@example.com", and the inner button may be unreachable in virtual cursor.
- Evidence: AX: `button "kaan@example.com Remove kaan@example.com"` plus `button "Remove kaan@example.com"`. axe `nested-interactive` (serious) fails on 4 chip stories (and `components-select--searchable-clearable`, where the clear button sits inside `role=button` — same defect class for Select).
- Why it matters: Wrong announcement, and an unreliable remove action for screen-reader users. This fails WCAG 4.1.2.
- Correct solution: Make the chip a *container* (no role, or `role=listitem` inside a `role=list`/`group`) with two sibling controls: an optional body `<button>` (when clickable) and the remove `<button aria-label="Remove X">`. This is the pattern in Material Web `md-input-chip`, Spectrum `sp-tag` with `sp-clear-button`, and Carbon `DismissibleTag`. For Select, move the clear button out of the trigger element (sibling in the control row).
- Effort: M

### AX-12: Brand text colours fail 4.5:1
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: brand tokens in `packages/tokens/src/brand/tulpar/light.ts` (brand text on surface; placeholder/label-muted; gold/ulgen tones).
- Problem (axe `color-contrast`, 47 stories):
  - Outlined, ghost and link button label `#00a468` on `#fff`: **3.22:1**. Tonal on `#deffea`: **3.01:1**.
  - `color="ulgen"` solid: `#15110b` on `#886816` **3.61:1**. Premium variant: `#ecb32a` on white **1.90:1**, on `#fff3d9` **1.72:1**.
  - Float / float-in labels **resting inside the field** (they *are* the label) and select placeholder/value: `#909396` on `#fff` **3.08:1**, on filled `#f0f7f5` **2.84:1**.
  - Shell: white on `#00c57a` 2.26:1 and `#21d98d` 1.84:1 (badge/count in `utility-end`/footer slots — story content, Plausible as a component default). `#00c57a` on `#deffea` 2.11:1.
- Evidence: `review\a11y-work\axe-all.json`. Summary from `cc.js` (in the same folder). Disabled-state failures were excluded (exempt).
- Why it matters: WCAG 1.4.3 (AA) failures on the default button variants and on field labels. Enterprise procurement (VPAT/508) fails on this.
- Correct solution: Make the brand step used for *text* on light surfaces a darker step (green ~700, ≥4.5:1 on white and on the tonal tint). Keep the bright step for fills and large text only. Encode this as separate semantic tokens `color.brand.text` vs `color.brand.fill` (Radix Colors step 11 vs 9; Primer `fg.accent` vs `bg.accent-emphasis`). Give placeholder and float labels a token ≥4.5:1 (Carbon `$text-placeholder` is ≥4.5:1 after 2023). Add a token-level contrast matrix test for *every* text-on-surface pair in light and dark (the overlay test is the model, after fixing AX-7's alpha bug).
- Effort: M

### AX-13: Ghost chip text invisible in dark mode (1.04:1)
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: chip ghost variant colours (`chip/tulpar-chip.styles.ts`), story `display-status-chip--dark-mode`.

### AX-14: Shell skip link does not move focus
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `packages/shell/src/shell/tulpar-shell.ts:254` (`<a href="#tulpar-shell-content">`), `:259` (`<main id=…>` inside the shadow root).
- Problem: Fragment navigation looks up ids in the *document*, not in the shadow root, and `<main>` has no `tabindex=-1`. Pressing Enter changes the URL hash, but focus stays on the skip link, and the next Tab goes to the topbar.
- Evidence: `sk.js`: `after Enter: url hash=#tulpar-shell-content focus=tulpar-shell>a{Skip to content}`, `next Tab -> tulpar-topbar>button[Toggle navigation]`. The link becomes visible on focus (133×38 at 8,8), which is correct.
- Why it matters: The bypass mechanism does nothing (WCAG 2.4.1 — partially rescued by the `main` landmark, but sighted keyboard users get no help). It also writes a hash into consumer router URLs.
- Correct solution: Handle the click: `preventDefault()`, then `main.focus()` with `main tabindex="-1"`. Optionally use `scrollIntoView`. Do not touch `location.hash`, because SPA routers own it. This is how GOV.UK Frontend's skip link works (it focuses the target and sets tabindex=-1).
- Effort: S

### AX-15: Tag sets `role="status"` on every tag
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: `tag/tulpar-tag.ts:94-95`.
- Problem: `status` is a live region. Every static tag (for example "Active" in a table row) becomes a polite live region. Any text change (re-render, virtualization, sort) gets announced. A future grid with thousands of tag cells would flood the screen reader.
- Evidence: AX `display-status-tag--default`: `status "" live="polite"`.
- Why it matters: Spurious announcements and wrong semantics (a tag is not a status message). This conflicts with WCAG 4.1.3 intent.
- Correct solution: No role by default (plain text). Consumers who want an announcement wrap the region themselves. Carbon `Tag`, Spectrum `sp-badge` and Polaris `Badge` have no live role. If tone conveys meaning, add visually hidden tone text (e.g. "Status: success") rather than colour only.
- Effort: S

### AX-16: Target size < 24×24 (WCAG 2.5.8)
- Severity: Major
- Merge-blocking for current branches: No
- Confidence: Verified
- Where: number-input steppers, `form-field-base` affordance buttons, `select-clear`, `toast-close` (`toast/tulpar-toast.styles.ts:258`), `shell sidenav-toggle`.
- Problem / Evidence (`ts.js` sweep and axe `target-size` on 2 stories):

  | Control | Measured |
  |---|---|
  | Number input increment/decrement | **18×10** each, stacked (no spacing exception possible) |
  | Text input clear/copy/paste | 18×18, adjacent (axe: "safe clickable space 20px") |
  | Textarea copy/paste | 24×20 |
  | Select clear | 18×18 |
  | Toast close | 20×20 (passes only through the spacing exception) |
  | Sidenav "Collapse sidebar" | 15×23 |
  | Chip xs | 22×16 |

- Effort: S

## Things done well
- **Reduced motion is handled with intent, not a global kill.** With reduce on: the spinner switches from rotate to a `tulpar-spinner-dots` pulse, indeterminate progress uses `tulpar-progress-pulse`, the button loader uses `tulpar-button-pulse`, skeleton shimmer is off, and the toast ring-deplete is off (`rm.js`).
- **Overlay focus management is APG-correct.** The popover moves focus into a `dialog "Account"` (`modal=false`), and Escape returns focus to the trigger. The tooltip shows on focus, is exposed as `tooltip` + description, and Escape dismisses it. The toggletip has `aria-expanded` and a pre-existing polite live region that is filled on open.
- **The native-element based fields are right.** TextInput, Textarea and NumberInput get the correct name through `<label for>`, `aria-describedby` to the message in the same scope, `aria-invalid`, and `aria-required`. The Switch (native `<button role=switch>`) is correctly named.
- **Select data-mode resolves `aria-activedescendant` correctly**, and Escape returns focus to the trigger in all modes.
- **Roving keyboard models work:** radio arrows check and move, ButtonGroup is a `toolbar` with arrows, Space and Enter toggle Checkbox and Switch, chip Delete/Backspace remove and focus moves to the neighbour.
- **Shell landmarks:** `navigation "Main navigation"`, `main`, `aria-current="page"`, a visible-on-focus skip link (the target needs AX-14), and named header toggles.
- **Avatar and Badge semantics:** `role=img` with a meaningful name ("8 notifications") and decorative internals `aria-hidden`.
- **Forced colors on buttons, chips and field borders** use `CanvasText` outlines and survive.

## Open questions for the owner
1. **Fix strategy for the cross-shadow ARIA family (AX-1/2/3/4/9).** Option (a): keep custom-role spans and wire every IDREF *inside* the shadow root (smallest change). Option (b): move to native inputs or host-as-control with ElementInternals ARIA (`internals.role`, `ariaChecked`), as Material Web and Web Awesome 3 do. (b) is more robust and aligns with the grid's future needs, but it is a bigger refactor. Which do you want?
2. **Release gating.** Should a WTR test that reads the *computed* accessibility tree be mandatory for every control (not just attribute assertions)? It would have caught AX-1/2/3/4/9 at the time they were built.
3. **Brand green as text colour (AX-12).** Do you accept splitting `brand.text` (darker, ≥4.5:1) from `brand.fill`? This visibly darkens the outlined/ghost/link button labels.
4. **Select searchable trigger role (AX-2/AX-5).** Keep the trigger `combobox` (APG select-only) and put the search combobox in a popup sibling to the listbox, or turn searchable mode into a full editable combobox (input in the trigger)? Both are valid APG patterns; the current hybrid is not.
