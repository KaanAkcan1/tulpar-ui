# Tulpar UI v0.15 — Select completion (`options` data-prop + in-popup search)

**Status:** Draft — pending spec-review loop + user approval
**Date:** 2026-06-24
**Predecessor:** v0.14 Select (single) — merged to `main` via PR #15. Reuses `<tulpar-select>`,
`<tulpar-option>`, `<tulpar-option-group>`, the `_internal/listbox/` brain, and `<tulpar-spinner>`.
**Type:** Additive API on the shipped `<tulpar-select>` + a new `_internal/listbox/` filter helper +
Angular/Vue wrapper forwarding + playground/stories. **No new public custom element.**
**Roadmap:** Closes the **binding deferred** Select work from v0.14, completing the Select slice of
**Wave 2 — Overlay-anchored data entry & menus** (see [`docs/roadmap.md`](../../roadmap.md)).

---

## 1. Overview

v0.15 finishes `<tulpar-select>` by adding the two binding items deferred from v0.14:

1. **`options` data-prop** — author a Select from a typed data array instead of slotted
   `<tulpar-option>` children. This is the form the future **data grid** will feed cell editors and
   column filters, and it is the API surface **Combobox / MultiSelect** will inherit.
2. **In-popup search (`searchable`)** — an opt-in search input inside the listbox that filters the
   visible options, with diacritic/locale-insensitive matching and match highlighting. This is a
   **select-only** filter (the committed value is always one of the options) — **not** the free-text
   Combobox (that remains the next Wave-2 slice).

The **mobile-native `<select>` fallback** is explicitly deferred again (§10): it forks behavior, conflicts
with rich two-line/icon options, and carries lower grid value than the two items above.

### Goals
- A `<tulpar-select options=[…]>` data path that renders **real `<tulpar-option>` / `<tulpar-option-group>`
  elements** internally, so the entire shipped listbox machinery (styling, `aria-selected`/`data-selected`
  reflection, `aria-activedescendant`, click/hover delegation, form value) works **unchanged**.
- A typed, exported option model (`SelectOption` / `SelectOptionGroup`) that mirrors the slotted
  `<tulpar-option>` / `<tulpar-option-group>` structure — no ambiguity, no new mental model. (One small
  parity gap is closed along the way: the slotted `<tulpar-option-group>` gains a `disabled` prop so group
  disabling exists in **both** forms, §3.1.)
- An opt-in `searchable` mode that adds an in-popup filter input with correct focus + keyboard semantics,
  reusing the **same `resolveKeyAction` + active-descendant controller** as the non-searchable path.
- Diacritic/Turkish-insensitive substring matching against the option **label**, with the matched run
  **highlighted** in text labels; a first-class **no-match** state distinct from the empty state.
- A reusable, unit-tested `filter(query)` helper in `_internal/listbox/` that Combobox/MultiSelect adopt
  without a rewrite.
- Angular + Vue wrappers updated (new props/slot forwarded), **playground parity** (ng + vue), Storybook
  stories, WTR + Playwright verification.

### Non-Goals (binding) — see §10
**Mobile-native `<select>` fallback** · custom **`filterFn`** prop (deferred to Combobox, where custom
matching truly lands) · **free-text Combobox** · **MultiSelect** · **virtualization** · **async/remote
options loading** (the `loading`/`error` listbox states already exist for an app-driven async flow, but no
built-in fetch/debounce is added here).

### Cross-cutting principle: prop AND slot, never one instead of the other
Per [[feedback_optional_prop_does_not_remove_slot]], the new text affordances keep both forms: the
`no-match` message has a `no-match-text` prop **and** a `no-match` slot (slot wins). `options` is the one
deliberate exception to "prop sits on top of slot": it is a **list-source selector**, not a single content
slot, so data-mode and slotted-mode are **mutually exclusive** (§3.1) — mixing two list sources in one
control is the documented ambiguity we reject.

### 2.1 Data-mode rendering — render real `<tulpar-option>` into the shadow listbox (load-bearing decision)

The constraint that shaped v0.14 still holds: the listbox lives in the Select's **own shadow DOM**, and
slotted `<tulpar-option>` light-DOM children project through a `<slot>` inside it. Data-mode does **not**
relocate anything — when `options` is set, the Select **maps the data array to real `<tulpar-option>` /
`<tulpar-option-group>` elements rendered directly in the shadow listbox template** (alongside the
always-present default `<slot>`, which simply projects nothing in data-mode).

Why render real `<tulpar-option>` (not plain `role=option` divs):
- The active-descendant controller, selection reflection (`aria-selected`/`data-selected`), hover/click
  delegation, and `_options()` all key off the `<tulpar-option>` element (`it.el`, `node.tagName ===
  "TULPAR-OPTION"`). Rendering the real element keeps **all of that unchanged** — data-mode is "where the
  options come from," not "a second rendering path."
- Styling, size geometry, description/two-line layout, and the selected three-signal treatment come for
  free from the shipped `tulpar-option` styles.

Declarative stamping in data-mode: ids (`id=tulpar-opt-…` for `aria-activedescendant`) and `data-size` are
assigned **in the Lit template** when mapping the data, so the imperative `_ensureOptionIds()` /
`_syncOptionSizes()` stamping is **not** needed for data options (it remains for the slotted path). A stable
id derivation keyed off option `value` (deduped) avoids id churn across re-renders.

> **CRITICAL Lit-trap guard (unchanged from v0.14):** the default `<slot>` inside the listbox must remain
> **always present and never conditionally swapped**, or the `slotchange`→`requestUpdate()` handler locks
> the page ([[reference_lit_slotchange_requestupdate_loop]]). Data-mode renders the mapped options **as
> siblings of** the slot, never by removing/replacing the slot. The `slotchange` handler early-returns when
> `options` is set (slotted children are inert in data-mode).

### 2.2 `_options()` generalization (single reader, two sources)

`_options()` becomes source-aware:
- **data-mode** (`this.options != null`): read the shadow-rendered options via
  `this.renderRoot.querySelectorAll("tulpar-option")` in document order.
- **slotted mode** (`this.options == null`): the existing `this.querySelectorAll("tulpar-option")` over
  light DOM — **byte-for-byte the v0.14 behavior**.

Everything downstream — `buildCollection`, `_selectedLabel`, `indexByValue`, form value, the active and
selection controllers — consumes the resulting `OptionLike[]` and is **unchanged**. This keeps the two
sources behind one boundary: the rest of the component never asks "where did the options come from."

**Imperative stampers go no-op in data-mode.** `_ensureOptionIds()` and `_syncOptionSizes()` query light
DOM (`this.querySelectorAll`) and exist for the slotted path; in data-mode ids + `data-size` are assigned
**declaratively in the template**, so both stampers **early-return when `options != null`** (they must not
fight the template). `_onOptionsSlotChange` likewise early-returns in data-mode (the slot projects nothing
to refresh). `_syncLeadingIcon()` naturally no-ops (data options carry no `slot="icon"`).

### 2.3 The `filter.ts` listbox unit (the reusable matcher)

A new pure, DOM-light, independently unit-tested unit in `_internal/listbox/`:
- `normalize(s)` → `{ text: string; map: number[] }` — folds **one original char to exactly one output
  char** (a 1:1 char map, NOT NFD expansion), so output length equals input length and `map[i]` is the
  identity. The fold: `toLowerCase()` then a Turkish/diacritic table (`İ→i`, `I→i`, `ı→i`, `ş→s`, `ğ→g`,
  `ç→c`, `ö→o`, `ü→u`, plus the common Latin set `á/à/â/ä→a`, `é/è/ê/ë→e`, `í/ì/î/ï→i`, `ó/ò/ô/ö→o`,
  `ú/ù/û/ü→u`, `ñ→n`, …). Because the map is strictly 1:1, **highlight ranges never misalign** and there is
  no length-change fallback. (Rationale: a 1:1 table sidesteps the one lossy NFD case — `İ` U+0130
  decomposing to `i`+combining-mark — that would otherwise shift indices.)
- `filterOptions(labels, query)` → `{ matched: boolean[]; ranges: Array<[start,end] | null> }` — for each
  label, normalize both sides, `indexOf` the normalized query; on hit, `matched[i]=true` and
  `ranges[i]=[start, start+query.length]` mapped **back to original-label indices** via the 1:1 `map`
  (identity here, but the map keeps the API honest if a future fold becomes non-1:1).
- Empty/whitespace-only query → `matched` all `true`, `ranges` all `null` (no highlight).

Per the `_internal` rule it stays package-private; one consumer now (Select), shaped so Combobox's free-text
filter and MultiSelect adopt it directly. No premature extraction to a package (waits for a real second
consumer per [`docs/architecture/internal-layering.md`](../../architecture/internal-layering.md)).

### 2.4 Unit boundaries
`tulpar-option` stays a dumb display element — it gains **one** capability: when the parent passes a
highlight range (text-label only), it wraps the matched run in a `<mark part="match">`. It holds no filter
logic. All filtering orchestration lives in `tulpar-select` + the pure `filter.ts`. `select-options.ts` is
types + a `isOptionGroup()` guard, no behavior.

### 2.5 Filter-driven visibility — the one shared-brain change (load-bearing)

Filtering must hide non-matching options **without renumbering** the option list, because
`aria-activedescendant` ids, `composedPath` option lookups (`items.findIndex(it => it.el === node)`),
`applyActiveAttrs`, and `scrollActiveIntoView` all rely on the collection index ↔ rendered DOM element
correspondence. So the chosen approach is **(a) carry a `hidden` flag, keep every item in the collection** —
**not** (b) excluding hidden items (which would break that correspondence and the empty-vs-no-match check).

Concretely this is the **only** change to the shared `_internal/listbox` brain:
- **`collection.ts`** — `OptionLike` and `CollectionItem` gain an optional `hidden?: boolean`. `_options()`
  sets `hidden` from the current filter result (an option whose label did not match). Selection/label/value
  lookups (`indexByValue`, `labels`) are unchanged; `items.length` still counts all options.
- **`active-index.ts`** — `ActiveItem` gains `hidden?: boolean`, and **every skip check changes from
  `!disabled` to `!disabled && !hidden`** (in `firstEnabled`/`lastEnabled`/`nextEnabled`/`prevEnabled`/
  `pageMove`/`clampActive`). Result: arrows/Home/End/Page and open-seeding traverse only **enabled +
  visible** options, no-wrap unchanged. With no filter active, `hidden` is everywhere `false` → behavior is
  byte-for-byte v0.14.
- The rendered `<tulpar-option>` gets the native `hidden` attribute (removed from layout) when its
  collection item is hidden; a `<tulpar-option-group>` whose every child is hidden also gets `hidden`
  (header disappears).

This is called out as a **foundation change** (not "reused unchanged") because Combobox/MultiSelect inherit
the same `hidden`-aware navigation; specifying it once here is deliberate.

## 3. Public API additions

### 3.1 `options` data-prop on `<tulpar-select>`

**Types** (exported from core, e.g. `select/select-options.ts`):
```ts
export interface SelectOption {
  value: string;
  label: string;
  disabled?: boolean;
  description?: string; // optional second line (two-line option)
}
export interface SelectOptionGroup {
  label: string;
  disabled?: boolean;          // disables every option in the group
  options: SelectOption[];
}
export type SelectOptions = ReadonlyArray<SelectOption | SelectOptionGroup>;
```

| Member | Type | Default | Notes |
|---|---|---|---|
| `options` | `SelectOptions \| null` (property) | `null` | When non-null → **data-mode**. Set via property binding (object/array, not an attribute). `null`/unset → slotted mode (unchanged). |

- **Precedence — mutually exclusive, prop wins.** `options != null` → data-mode; slotted children are
  ignored (the slot projects but data-mode reads shadow options). `options == null` → slotted mode is
  byte-for-byte v0.14. No concat, no mixing.
- **Icon is slot-only.** Data options carry no icon (Tulpar has no Icon component — out of scope). The
  leading-icon trigger sync (`_syncLeadingIcon`) finds nothing in data-mode → no-op, consistent. Rich
  icon authoring uses the slotted form, which still exists.
- **Disabled group:** `SelectOptionGroup.disabled` renders every child option `disabled` (skipped by nav +
  typeahead) and dims the group header. The slotted `<tulpar-option-group>` has **no `disabled` today**, so
  this spec **adds a `disabled` prop to the slotted group element** too (a tiny `tulpar-option-group.ts`
  change) so the capability exists identically in both data-mode and slotted-mode — true parity, not a
  data-mode-only feature.
- **Value/selection** works identically: `value` matches against `SelectOption.value`; an unmatched `value`
  shows the placeholder (same as slotted).
- **Duplicate / missing `value`** dev-warns (same policy as slotted options).

### 3.2 `searchable` (in-popup search) on `<tulpar-select>`

| Member | Type | Default | Notes |
|---|---|---|---|
| `searchable` | boolean (attr+prop, reflect) | `false` | Opt-in. Adds a sticky search input at the top of the listbox. Works in **both** data and slotted modes. |
| `searchPlaceholder` | string (`search-placeholder`) | `"Search…"` | Placeholder of the in-popup search input. |
| `noMatchText` | string (`no-match-text`) | `"No matches"` | Status row shown when the query matches nothing. Distinct from `emptyText` ("no options exist"). |

- **Slot:** `slot="no-match"` overrides `noMatchText` (slot wins), mirroring the existing
  `empty`/`loading`/`error` slot pattern.
- **Typeahead interplay:** when `searchable` is on, the 500ms typeahead-jump is **disabled** (typing into
  the search input filters instead — having both would double-handle keystrokes). Non-searchable Selects
  keep typeahead exactly as in v0.14.
- **`clearable`** is unaffected and composes with `searchable`.

### 3.3 `<tulpar-option>` highlight (internal-facing)
`tulpar-option` gains a parent-set highlight hook used only by the Select while filtering: the Select passes
the matched range; the option wraps that run of its **text label** in `<mark part="match">`. When the
label is slotted rich content (not plain text), the option renders it unhighlighted (filtering still works;
only the visual highlight is skipped). No new consumer-facing prop.

## 4. Interaction & accessibility

### 4.1 ARIA — role moves to the search input in searchable mode
- **Non-searchable (unchanged from v0.14):** the trigger is `role="combobox"` +
  `aria-haspopup="listbox"` + `aria-expanded` + `aria-controls` + `aria-activedescendant`. APG
  "Select-Only Combobox."
- **Searchable:** combobox semantics move to the **in-popup search `<input>`**:
  `role="combobox"`, `aria-autocomplete="list"`, `aria-controls=<listbox id>`,
  `aria-expanded="true"` (while open), `aria-activedescendant=<active option id>`, `aria-label` =
  "Search <field label>" (or a `search-placeholder`-derived label). The **trigger** drops to an opener:
  `aria-haspopup="listbox"` + `aria-expanded` + `aria-controls`, **without** `role="combobox"` or
  `aria-activedescendant` (so exactly one combobox role is active at a time, never two).
- **Render path:** `renderControl()` today hardcodes `role="combobox"` + `aria-activedescendant` on the
  trigger. This becomes **conditional on `searchable`**: when `searchable`, the trigger renders as the
  opener (no combobox role, no activedescendant) and the search input (rendered inside the listbox, §5.1)
  carries the combobox role + `aria-activedescendant`; when not `searchable`, the trigger is exactly the
  v0.14 combobox. The active-descendant controller's `getTrigger()` target for the `aria-activedescendant`
  write is therefore the search input in searchable mode and the trigger otherwise — a single
  "active-host" accessor the controller already centralizes.
- Listbox/option/group roles (`listbox`/`option`/`group`) unchanged. `aria-selected`/`data-selected`
  reflection unchanged.

### 4.2 Focus & keyboard model (searchable) — keymap stays the single source of truth

The searchable handler **must still route through `resolveKeyAction`** (the file's stated "keyboard
CONTRACT"), so the resolver is **extended**, not bypassed. `KeyState` gains two fields and the action union
gains one member:
- `KeyState`: `+ searchable: boolean` `+ hasQuery?: boolean` (whether the search query is non-empty;
  optional — only read inside the `searchable` branch, so non-searchable callers need not pass it).
- `KeyActionType`: `+ "clear-query"` (clear the search input, keep the listbox open).

Resolver changes **only when `state.searchable` is true** (non-searchable behavior is byte-for-byte v0.14):
- **`Escape`** → `state.hasQuery ? "clear-query" : "revert"`. This is the two-stage Escape, expressed in the
  pure resolver (no host-side interception). `clear-query` keeps the popup open + focus in the input; a
  second Escape (now `hasQuery=false`) reverts + closes (`stopPropagation`, focus → trigger).
- **`Space`** → **`"none"`** (a space is text in the search input — it must type, not commit). Only `Enter`
  and `Tab` commit in searchable mode.
- **Printable chars** (open: `"typeahead"`; closed: `"open-typeahead"`) → **`"none"`** so the keystroke
  reaches the `<input>` and the input's own `input` event drives filtering. (Typeahead is dead in
  searchable mode — the filter replaces it.) Closed-state `Enter/Space/ArrowDown/ArrowUp` still `"open"`.
- `ArrowDown`/`ArrowUp`/`Home`/`End`/`PageDown`/`PageUp`/`Enter`/`Tab` are **unchanged** (still
  `preventDefault: true` for arrows/Home/End/Page so the text caret doesn't move; `move-*`/`first`/`last`/
  `page-*` now traverse **enabled + visible** options via the §2.5 `hidden`-aware `active-index`).

Host wiring:
- **Keydown listener placement.** In searchable mode focus lives in the search `<input>` (not the trigger),
  so a keydown listener is attached to the **search input** that routes through the **same**
  `resolveKeyAction` as the trigger handler (the existing `_onTriggerKeydown` stays for the non-searchable
  trigger path). Both call sites pass `searchable: this.searchable` and `hasQuery: this._query !== ""`.
- **Open** (click trigger or open-keys) → DOM focus moves to the search input; query is **reset**; active
  index seeds to the selected option if visible, else the first enabled **visible** option;
  `scrollActiveIntoView()`.
- The `input` event on the search field updates `this._query`, re-runs `filterOptions`, applies `hidden` to
  the collection/DOM (§2.5), and re-seeds active to the first enabled visible match (or `-1` → no-match).
- `"clear-query"` action → set `this._query = ""`, re-filter (all visible), re-seed active, keep open.
- **Non-searchable** keyboard model is **unchanged** (trigger keydown, typeahead, all v0.14).
- **Hover** still unifies with active (pointer-over sets active), unchanged.

### 4.3 Filtering behavior
- Match: `filterOptions(labels, query)` over the **label** (normalized: case + diacritic + Turkish fold,
  §2.3). Description is **not** matched in v0.15 (label is the searchable identity; matching description was
  weighed and deferred to keep results predictable — reserved as a future `searchFields` option).
- Non-matching options get `hidden` (removed from layout **and** from keyboard nav — `_options()`/collection
  treats `hidden` options as non-navigable). A group whose every option is hidden has its **header hidden**
  too.
- **Highlight:** the matched run in each visible option's **text label** is wrapped in `<mark part="match">`
  (subtle brand-tinted background, no color-only reliance — it is bg + weight). Data-mode labels are always
  text → always highlightable. Slotted rich labels skip the highlight (filter still applies).
- **No-match vs empty (explicit render predicate).** Because filtering hides options but keeps them in the
  collection (§2.5), `items.length` never reaches 0 on a filter, so the existing empty branch alone is
  insufficient. `_renderStatusRow` resolves in this priority order:
  1. `loading` → loading row (unchanged);
  2. `error`/error-slot → error row (unchanged);
  3. **no-match** — `searchable && this._query !== "" && items.length > 0 && items.every(i => i.hidden)`
     → `role="status"` row using `noMatchText` / `no-match` slot. The search input stays focused.
  4. **empty** — `items.length === 0` (no options exist at all) → existing empty row (unchanged).
  The no-match branch is checked **before** empty and is mutually exclusive with it (no-match needs
  `items.length > 0`; empty needs `=== 0`).
- **Query reset:** the query is cleared on **every close/open cycle** (consistent with v0.14's
  value-snapshot + typeahead reset on open). Reopening always starts unfiltered.

### 4.4 Dismissal & focus restore (unchanged contract)
Every close path still returns DOM focus to the **trigger** (in searchable mode, focus is in the popup input
while open, and restores to the trigger on close). Outside-pointerdown, scroll/resize dismissal, and the
Escape stack are unchanged from v0.14 (the search input is inside the panel, so it is part of the
"trigger ∪ panel" union for outside-click). **Tab from the search input:** the `commit` action fires with
`preventDefault:false`, then the host closes the popup on the resulting focusout (focus leaves the
trigger∪panel union); focus continues to the next field — same net effect as the v0.14 trigger Tab, and the
top-layer `popover="manual"` panel does not trap Tab.

## 5. Visual design

Reuse the v0.14 listbox/option visual language verbatim; only two new surfaces.

### 5.1 Search input (sticky top of listbox)
- A slim input pinned to the top of the scroll container (`position: sticky; top: 0`), above the options,
  below any group sticky headers' stacking. Background `--tulpar-overlay-surface-bg` so options scroll
  beneath it cleanly; a 1px bottom hairline (`--tulpar-overlay-surface-border`) separates it from the list.
- Sized to the active tier (height tracks the option row height for the size; font matches option font).
  Leading 14px search (magnifier) glyph in `--tulpar-input-icon-default`; placeholder
  `--tulpar-input-text-placeholder` (no italic). Reuses input text tokens — **no new tokens**.
- Reduced-motion / forced-colors: inherits the panel's existing treatment; the input border uses
  `CanvasText` under forced-colors.

### 5.2 Match highlight
- `<mark part="match">` inside an option label: background
  `color-mix(in srgb, var(--tulpar-color-brand-default) 14%, transparent)`, inherit text color,
  `font-weight: 600`, `border-radius: 2px`, no padding shift. Never color-only (it is bg + weight).
- Forced-colors: `<mark>` → `Mark`/`MarkText` system pair (browser default, honored).
- `part="match"` is exposed so a consuming app can retheme the highlight.

### 5.3 No-match row
Reuses the v0.14 `.select-status` row treatment (`data-kind="no-match"`), centered muted text, the same
geometry as empty/loading/error rows so the panel height stays stable when the query empties the list.

### 5.4 Tokens
- **No new semantic tokens.** Search input → `--tulpar-input-*` + `--tulpar-overlay-surface-*`; highlight →
  inline `color-mix` on `--tulpar-color-brand-default` (the established selection-tint recipe); no-match row
  → `--tulpar-color-text-muted`. A dedicated `--tulpar-select-match-*` role is **deferred** until a second
  brand needs to retune it (internal-layering "promote on second consumer").

## 6. Wrappers (parity mandatory)

### 6.1 Angular (`@tulpar-ui/angular`) — signals only
`<tulpar-select-ng>` gains: `options` as an `input<SelectOptions | null>()` bound as a **property** (object
array, not attribute); `searchable`, `searchPlaceholder` (`search-placeholder`), `noMatchText`
(`no-match-text`) as `input()`s; `no-match` slot forwarded. The existing `(changed)` output and
`model('value')` are unchanged. No RxJS ([[feedback_angular_signals_only]]). The `SelectOptions` types are
re-exported from the Angular package for consumer typing. Verify in the Angular playground including dark +
the wrapper-nesting attr-mirroring caveat ([[reference_angular_sidenav_wrapper_nesting]]).

### 6.2 Vue (`@tulpar-ui/vue`)
`<TulparSelect>` gains `:options`, `searchable`, `search-placeholder`, `no-match-text` props and a
`#no-match` slot **forwarded through the transparent `display:contents` carrier** (the documented Vue WC
slot trap — CLAUDE.md "Vue wrapper slot forwarding"). `v-model:value` + `@change` unchanged. `SelectOptions`
types re-exported.

## 9. Accessibility checklist (WCAG 2.2 AA)
- Exactly **one** `role="combobox"` active at a time (trigger when closed/non-searchable; search input when
  searchable+open). `aria-activedescendant` always points at the active option; never roving DOM focus.
- Search input has an accessible name (label derived from the field label); `aria-autocomplete="list"`.
- Filtering announced: `aria-activedescendant` updates as the active option changes; no-match row is
  `role="status"` (polite). `aria-busy` while `loading` unchanged.
- Highlight never color-only (`<mark>` = bg + weight); forced-colors honored (`Mark`/`MarkText`,
  `CanvasText` borders).
- Focus restore to the trigger on every close path; `:focus-visible` ring on the search input.
- `prefers-reduced-motion` honored (no new motion introduced).

## 11. Out of scope (binding) + reserved surface
**Deferred (binding — do not pull forward):**
- **Mobile-native `<select>` fallback** — forks behavior + conflicts with rich (two-line/icon) options +
  lower grid value. *Reserved:* keep the trigger/positioner open to a future `native-on-mobile` flag at the
  shell breakpoint.
- **Custom `filterFn` prop** — deferred to **Combobox**, where custom/remote matching is the core feature.
  *Reserved:* `filter.ts` is a pure function the Select calls, so a `filterFn` override is additive later.
- **Matching `description` (and a `searchFields` option)** — v0.15 matches label only. *Reserved:*
  `filterOptions` takes the strings to match, so feeding description text later is additive.
- **Free-text Combobox** (value not constrained to an option) — next Wave-2 slice.
- **MultiSelect** — next Wave-2 slice; *reserved:* `value` stays a single string here.
- **Virtualization** — incompatible with slot-owned nodes; data-mode makes it *more* feasible later
  (Select owns the option elements), but it is out of scope now.
- **Async/remote options** — no built-in fetch/debounce; apps drive `options` + `loading`/`error` states.

## 13. Resolved decisions (recap)
- v0.15 scope = **`options` data-prop + in-popup `searchable`**; mobile-native fallback deferred (binding).
- `options` vs slotted = **mutually exclusive, prop wins**; data-mode renders **real `<tulpar-option>`/
  groups in shadow**; `_options()` reads shadow in data-mode, light DOM in slotted mode.
- Data shape = `(SelectOption | SelectOptionGroup)[]`, nested groups + `description`; **icon slot-only**.
- `searchable` = opt-in prop (default false), works in both modes; combobox role moves to the **search
  input** while open; typeahead disabled while searchable.
- Filter = label-only, **diacritic/Turkish-insensitive** via a **1:1 char fold** (highlight ranges never
  misalign), matched run **highlighted** (`<mark>` in text labels; skipped on slotted rich labels);
  **two-stage Escape via the keymap** (`clear-query`→`revert`); query reset per open; first-class no-match
  row (explicit render predicate, §4.3).
- **One shared-brain change (§2.5):** `collection.ts`/`active-index.ts` gain a `hidden` flag so nav skips
  filtered options without renumbering (keeps index↔DOM correspondence); `keymap.ts` gains
  `searchable`/`hasQuery` + `clear-query`. Combobox/MultiSelect inherit it.
- Slotted `<tulpar-option-group>` gains a `disabled` prop (parity with `SelectOptionGroup.disabled`).
- New pure `_internal/listbox/filter.ts`; **no new public custom element**; **no new tokens**; custom
  `filterFn` / description-matching / Combobox / MultiSelect / virtualization / mobile-native **deferred**.
